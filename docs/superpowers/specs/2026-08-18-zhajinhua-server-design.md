# 炸金花自建服务器版设计

日期：2026-08-18
状态：已完成分段设计，待用户审阅文档后进入实现计划

## 1. 目标与范围

将当前 Supabase 直连静态页面改造成可部署在单台 Ubuntu/Debian 服务器上的多人炸金花服务，保留牌桌核心玩法，并增加：

- 赢家按本局净收益成为下一局庄家并优先行动；下一局由新庄家手动点击开始。
- 梭哈只结束当前玩家行动，不因单个梭哈直接结算。
- 比牌阶段广播发起说明和即时胜负，但隐藏双方牌型，结算时再公开牌面与牌型。
- 账号邮箱注册/登录，不强制邮箱验证；匿名身份可迁移并绑定邮箱账号。
- 全局豆子、胜负统计、赌神榜/散财榜、称号、零余额手动补给和全站横幅。
- 观战身份、房主控制的观战开关和观战全局明牌。
- 独立排行榜页面、责任提示、动画、点击反馈和可记忆的音乐设置。

不在本阶段提供用户自助找回密码；管理员通过服务器端命令重置密码。

## 2. 已确认的产品规则

### 2.1 账号与迁移

- 新账号字段为邮箱、密码、全站唯一昵称。
- 注册后立即可玩，不等待邮箱验证。
- 已存在邮箱账号作为合并后的主账号；匿名账号余额与战绩相加，当前房间/座位迁移到主账号。
- 旧 Supabase 数据必须迁移。相同匿名用户跨多个旧房间时，迁移余额取所有房间中最高值，避免重复计算。
- 迁移使用一次性 Supabase service-role 导出和旧浏览器会话证明。服务端密钥只存在迁移环境变量或服务器文件中，不进入前端。
- 旧库没有完整不可变对局账本，无法可靠重建全部历史胜负次数；只能导入可验证的当前余额、活动房间和可解析的最近结算。

### 2.2 牌局与庄家

- 结算后按实际获得豆子最多者选为下一局庄家，且成为下一局首个行动者。
- 收益并列时按上一局行动顺序中最后完成获胜结算者决定庄家。
- 庄家在下一局开始前退出、转观战或豆子不足时，回退到本局净收益第二高且仍在房间的玩家。
- 结算后不自动开局，庄家必须点击“开始下一局”。
- 梭哈只标记 `all_in` 并结束该玩家行动；其他可行动玩家继续。仅当存活玩家不超过一人，或所有可行动玩家已匹配并完成行动时结算。所有人全押时可以自动结算，但不产生伪造的强制比牌动作。
- 比牌先广播“谁向谁发起比牌、费用”，计算后立即广播双方胜负给玩家和观战者；比牌阶段不展示双方牌和牌型，最终结算时公开。
- 账户实际返还按分池结算；界面显示净收益 `结算返还 - 本人本局总下注`。

### 2.3 账号豆子、榜单与称号

- 新账号初始 100,000 豆。
- 结算后净变化增加计胜局，减少计负局，持平不计。
- 赌神榜按胜局数降序；散财榜按负局数降序。豆子余额和总豆子只展示，不作为主排名键；同次数按昵称稳定排序。
- 赌神榜称号：第 1/2/3/4/5 名分别为 `赌神/赌圣/赌王/赌霸/赌鬼`。
- 散财榜称号：第 1/2/3/4/5 名分别为 `散财童子/赌鬼/赌霸/赌王/赌圣`。
- 同一玩家同时在两榜时只保留当前排名更靠前的称号；排名数字相同时赌神榜优先。
- 余额为 0 时玩家主动领取一次 100,000 豆，领取写入幂等账本；补给不自动触发。
- 每次余额归零时固定发送独立横幅：`{玩家昵称}：黄总是大帅比！`。如果该次刷新后成为散财榜第 1 名，再发送 `{玩家昵称}恭喜登上散财榜头名`。两类横幅使用独立队列，不互相覆盖。

### 2.4 观战与界面

- 排行榜不放在主牌桌，通过顶部导航按钮进入独立页面；页面提供两榜切换和返回牌桌。
- 房主可随时切换“允许观战”；关闭时不踢出现有观战者。
- 允许观战时，已入座玩家只能在等待或结算状态切换为观战并释放座位；观战者不占 8 人玩家上限。
- 观战者没有操作按钮，全局明牌，可看到下注、比牌说明、即时胜负和结算。
- 所有页面背景固定显示：`本游戏仅虚拟娱乐，禁止任何形式现金赌博，禁止线下结算，违者责任自负`。
- 动效提供轻量/影视两档，默认轻量；支持 `prefers-reduced-motion` 降级。
- 进入页面尝试自动播放音乐；浏览器拦截时不提示、不强行重试，玩家可自行开启。音乐开关保存到邮箱账号，跨设备同步；背景音乐和音效分别控制。

## 3. 服务架构

单台服务器运行三个职责进程：

1. HTTP API：账号、房间、玩家动作、榜单、设置和管理员命令入口。
2. 游戏 Worker：按房间取得 PostgreSQL advisory lock，推进唯一牌局状态，执行结算和经济事务。
3. WebSocket 网关：验证会话、管理房间/全站频道并广播事件，不直接决定牌局结果。

数据流：

`浏览器 -> HTTP API -> PostgreSQL -> 游戏 Worker -> 事件表/NOTIFY -> WebSocket 网关 -> 浏览器`

浏览器不再直连数据库。初期不引入 Redis，使用 PostgreSQL `LISTEN/NOTIFY` 与事件表；进程由 systemd 或 PM2 管理，Nginx 负责 HTTPS/WSS 反向代理。

## 4. 数据模型

- `users`：邮箱、Argon2id 密码哈希、昵称、余额、胜负次数、音乐设置。
- `sessions`：哈希后的会话令牌及过期时间。
- `rooms`：状态、房号、房主、庄家、当前行动、注额、底池、公开性、观战开关和版本号。
- `room_players`：座位、当前局投入、弃牌、全押、行动序号和临时筹码状态；唯一约束保证一个账号同时只坐一个玩家座位。
- `room_spectators`：观战用户与加入时间。
- `rounds` / `round_players`：每局快照、牌面、行动、结算和庄家选择。
- `account_ledger`：扣豆、返还、补给的不可变记录，带唯一幂等键。
- `global_banners`：全站横幅事件和队列序号。
- `legacy_migrations`：旧 Supabase 用户映射、旧余额最高值、迁移状态和一次性声明令牌。

所有涉及余额和胜负的改变在同一个数据库事务中完成：锁定房间/账号，校验动作，写账本，更新余额和统计，生成事件。前端不能直接更新经济字段。

## 5. 现有 Bug 根因与目标修复

- 当前 SQL 开局函数按最小座位写入 `current_turn`，没有庄家轮转字段；当前前端结算后 `syncAutoStart()` 还会自动调用 `startRound()`。新设计改为记录 `dealer_user_id/dealer_seat`，由结算事务选择收益最高者，且等待新庄家手动开始。
- 当前 `settleIfBettingComplete()` 在 `actionable.length === 0` 时立即结算，所有存活玩家全押时会直接进入结算，且没有明确的梭哈阶段说明。新 Worker 不把单个 `all_in` 当作结算信号，并在没有剩余可行动者时使用明确的自动结算事件。
- 当前 `hostCompare()` 把双方牌和 `typeName` 写进 `rooms.message`，渲染层立即显示；新事件拆成 `compare_started` 与 `compare_resolved`，均不包含牌型/牌面，`round_settled` 才公开。

## 6. 测试与验收

- 单元：牌型、边池、净收益、全押推进、比牌可见性、庄家选择/回退、榜单/称号、补给幂等。
- 数据库集成：并发下注、重复动作、结算原子性、昵称唯一、单房间座位、观战权限和管理员重置。
- 协议：HTTP 会话、动作幂等、WebSocket 房间/全站广播和玩家/观战者消息隔离。
- 浏览器：注册登录、建房入房、手动下一局、比牌隐藏牌型、全押继续、观战明牌、独立榜单、音乐记忆和免责声明。
- 迁移：只读导出报告、源数据数量/哈希、临时库导入抽样、旧会话绑定、备份和回滚演练。

## 7. 已知限制与后续决策

- 当前目录不是 Git 仓库，设计文档无法创建提交；应在后续初始化版本库后单独提交。
- 旧库没有完整历史账本，历史胜负榜只能从可验证数据开始累计。
- 没有用户自助找回密码；管理员重置流程必须保护服务器权限和审计日志。
- 实际部署前仍需确定域名、TLS 证书、SMTP（本阶段不发送验证/找回邮件）和 Supabase service-role 的短期迁移凭据保管方式。
